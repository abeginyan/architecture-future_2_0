# Будущее 2.0: архитектура платформы данных

Учебный проект курса «Архитектор программного обеспечения» (Яндекс Практикум, спринт 11). Кейс: группа компаний «Будущее 2.0» (клиники, ИИ-сервисы, финтех, головной офис, новые бизнесы). Единое хранилище данных (DWH) стало узким местом: отчёты строятся часами, финтех и ИИ не могут развиваться независимо, новые бизнесы сложно подключать, к данным предъявляют требования безопасности и регуляторы.

Пять бизнес-сценариев, которые встречаются во всех заданиях:

| Метка | Сценарий |
|-------|----------|
| S1 | Быстрая отчётность |
| S2 | Независимое развитие финтеха и ИИ |
| S3 | Масштабирование на новые бизнесы |
| S4 | Безопасность и требования регуляторов |
| S5 | Надёжность и доступность |

## Кратко по заданиям

### [Задание 1. Целевая архитектура и приоритизация проблем](Task1/)

Целевая архитектура на горизонте года: домены вместо одного DWH, отдельная платформа данных (озеро, быстрые витрины, BI, портал самообслуживания), единая безопасность, мультизонное облако. Медицинские данные в платформу не попадают. Проблемы старой системы сопоставлены со сценариями и упорядочены по важности. Функции ESB (проверки, преобразования, надёжность, бизнес-логика) распределены между Kafka, реестром схем, потоковой обработкой, сервисами доменов и API Gateway, миграция идёт по потокам. Старое DWH делится на две части: аналитическая уходит в чтение и архив, а клинический контур с записью приёмов и медкарт работает, пока перенос клиник не проверен.

Главные файлы: `C4_Container.png`, `problems.md`, `prioritization.md`, `esb_migration.md`, `clinical_contour.md`.

### [Задание 2. Домены и потоки данных](Task2/)

Система разделена на 7 доменов: клиники, ИИ-сервисы, финтех / банк, головной офис, партнёры, интеграция и безопасность, платформа данных. На DFD показаны потоки четырёх сценариев: ИИ-анализ медицинских данных, подключение финтех-сервиса, быстрая отчётность, подключение партнёров по шаблону. Идея: новый продукт, партнёр или отчёт не требует новой логики в DWH.

Главные файлы: `DFD.png`, `domains.md`, `data_flows.md`, `argumentation.md`.

### [Задание 3. Технологический радар и роадмап](Task3/)

Радар показывает, что выводим (MS SQL Server 2008, хранимые процедуры, Apache Camel, PowerBuilder), что внедряем (облако, Kubernetes, Kafka с реестром схем, PostgreSQL, Keycloak) и что пилотируем (Kafka Streams, Data Mesh, озеро на Iceberg, ClickHouse, dbt, каталог данных). Роадмап на 12 месяцев состоит из 4 этапов; к месяцу 6 первые отчёты за минуты, к 9 финтех и ИИ развиваются без правок в DWH, к 12 работает портал, подключён первый партнёр и пройден пилот новой клинической системы в одной клинике. Запись клиник в старый контур закрывается только по условиям проверенного переноса.

Главные файлы: `tech_radar.png`, `roadmap.png`, `roadmap.md`, `argumentation.md`.

### [Задание 4. Облачная инфраструктура на Terraform](Task4/)

Инфраструктура пилота описана кодом: сеть, 4 подсети, NAT-шлюз для приватных подсетей, группы безопасности, 4 виртуальные машины (`bastion`, `integration`, `data-platform`, `portal`), диски данных, статические публичные адреса и расписание снимков дисков. Проект развёрнут командой `terraform apply` в реальном Yandex Cloud; размеры уменьшены под квоты облака через отдельные файлы значений. В обосновании разобраны размеры ВМ и дисков, NAT, декларативный подход и преимущества IaC (воспроизводимость и масштабирование).

Главные файлы: `main.tf`, `variables.tf`, `outputs.tf`, `terraform.tfvars`, `diagram.png`, `justification.md`, `apply_screenshot.png`.

## Как открыть материалы

- Диаграммы (`*.png`) открываются как обычные картинки; исходники (`*.puml`) пересобираются в PlantUML (команды в README каждой папки).
- Таблицы и обоснования лежат в файлах `*.md` в каждой папке.
- Запуск Terraform описан в [Task4/README.md](Task4/README.md). Файлы `key.json`, `*.tfstate` и каталог `.terraform/` в репозиторий не добавляются.
