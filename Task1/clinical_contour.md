# Задание 1. Клинический контур: когда можно закрыть запись в старое DWH

Документ отвечает на замечание: к концу года DWH переводится в «только чтение», а для клиник в плане есть лишь прототип замены PowerBuilder. Если закрыть запись, клиники перестанут сохранять новые приёмы и изменения медкарт. Совпадение аналитических отчётов этого не проверяет: отчёты читают данные, а клиники их пишут.

Метки S1–S5 — те же бизнес-сценарии, что в [problems.md](problems.md). Новая проблема описана там же как **P15**.

## 1. Принцип

**Запись в старое DWH закрывается не по дате, а по условиям.** Пока клиники пишут в старый контур, он работает. Мы выключаем запись только после проверенного переноса клинических операций.

Для этого старое DWH делится на две части с разной судьбой:

| Часть | Что это | Что с ней делаем к концу года |
|-------|---------|-------------------------------|
| **Аналитическая часть DWH** | Исторические данные, отчёты, трансформации | Переводится в «только чтение», затем архивируется (как в плане) |
| **Клинический контур легаси** | PowerBuilder и данные, в которые клиники сейчас записывают приёмы, назначения и изменения медкарт | **Продолжает работать с записью**, пока не пройдены условия переноса (раздел 3) |

Так аналитика получает быстрый результат (S1) и не ждёт клиник, а клиники не теряют возможность работать (S5).

Предположение: сейчас клинические операции пишутся в то же DWH. Точный список операций, которые пишут данные, выясняется на шаге 0 (раздел 2).

## 2. План по шагам

| Шаг | Срок | Что делаем с клиническим контуром | Результат |
|------|------|-----------------------------------|-----------|
| 0 | Месяцы 1–2 | Инвентаризация **записи**: какие операции PowerBuilder создают и меняют данные (запись на приём, приём, назначения, правки медкарты, результаты исследований), кто и в каком объёме ими пользуется, какие потоки Camel с ними связаны | Перечень клинических операций с владельцами и частотой |
| 1 | Месяцы 3–6 | **Выделение клинических данных в отдельную БД** (MS SQL, остаётся с записью). PowerBuilder переключается на неё. Аналитика получает данные из неё по allow-list через Kafka, без медицинских наборов | Аналитическую часть DWH можно переводить в чтение, не останавливая клиники |
| 2 | Месяцы 6–9 | Аналитическая часть DWH переходит в «только чтение». Клинический контур продолжает работать | Первые отчёты на новой платформе, клиники не затронуты |
| 3 | Месяцы 6–12 | Клиническая информационная система (веб) разрабатывается по списку операций из шага 0 и проходит **пилот в одной клинике** (параллельная работа, сверка) | Подтверждённое покрытие операций, проверенный перенос данных |
| 4 | После пилота, по клиникам | Перенос клиник на новую систему **по одной**. Для каждой: обучение, окно переключения, откат | Клиника работает в новой системе, старый контур для неё закрыт на запись |
| 5 | После переноса всех клиник | Выключение клинического контура легаси и PowerBuilder, архив | Легаси отключено |

Годовой горизонт: к месяцу 12 завершены шаги 0–2, идёт шаг 3. Шаги 4–5 переносятся на время после пилота. Это совпадает с прежним решением, что полная замена легаси за год не требуется (Won't have), но теперь это явное условие, а не умолчание.

## 3. Условия отключения записи в клинический контур

Запись в клинический контур выключается для клиники только когда выполнены **все** пункты:

| № | Условие | Как проверяем |
|---|---------|---------------|
| 1 | Все клинические операции из перечня шага 0 работают в новой системе | Чек-лист операций, сквозные тесты по каждой, подпись главного врача и владельца домена |
| 2 | Данные перенесены без потерь | Сверка: число пациентов, приёмов, записей в медкартах, вложений (снимков); выборочная проверка записей врачами |
| 3 | Пилот в клинике прошёл без критичных сбоев | Параллельная работа не менее 4 недель; нет случаев, когда запись не сохранилась |
| 4 | Права и защита данных не хуже, чем в легаси | Роли в SSO, шифрование, журнал доступа; согласование с безопасностью |
| 5 | Персонал обучен, есть поддержка в первые недели | Доля обученных, дежурная команда на время запуска |
| 6 | Подтверждена отказоустойчивость новой системы | Резервные копии, проверка восстановления, мультизона |
| 7 | Готов откат | После переключения старый контур хранится доступным для чтения и включения записи ещё 1 месяц (с доведением данных обратно) |

Если хотя бы одно условие не выполнено, клиника остаётся на старом контуре.

## 4. Риски

| Риск | Чем грозит | Что делаем |
|------|-----------|------------|
| Клинические операции пропущены при инвентаризации | После переключения врач не может выполнить действие | Шаг 0 по записи, не только по отчётам; сверка списка с врачами; пилот в одной клинике |
| Пилот затягивается, срок года срывается | Легаси остаётся дольше | Это допустимо: клинический контур не мешает аналитике (отдельная БД), стоимость поддержки считаем и показываем бизнесу |
| Поддержка PowerBuilder и SQL Server 2008 (риск безопасности P1) | Устаревшая БД остаётся в клиническом контуре | Изоляция клинического контура: закрытая сеть, доступ только из рабочих мест клиник, обновлённые резервные копии, мониторинг; выделенная БД переносится на поддерживаемую версию СУБД |
| Расхождения данных при переносе | Потеря или искажение медкарт | Сверка, параллельная работа, откат |
| Врачи не принимают новую систему | Сопротивление, ошибки ввода | Пилот с участием врачей, обучение, обратная связь до массового запуска |

## 5. Что считаем успехом к концу года

| Показатель | Цель к месяцу 12 |
|------------|------------------|
| Клиники теряют возможность сохранять приёмы и медкарты | Нет |
| Аналитическая часть DWH в режиме «только чтение», отчёты работают на новой платформе | Да |
| Клиническая информационная система прошла пилот в одной клинике | Да |
| Клиник, где запись в легаси выключена без выполнения условий раздела 3 | 0 |
