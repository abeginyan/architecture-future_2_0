# Задание 3. Роадмап изменений «Будущее 2.0»

Диаграмма: [roadmap.png](roadmap.png) (скрипт: [build_roadmap.py](build_roadmap.py)). Технологии из радара: [tech_radar.md](tech_radar.md). Этапы совпадают с порядком работ из Задания 1, домены и потоки — из Задания 2.

Метки сценариев: **S1** быстрая отчётность · **S2** независимое развитие финтеха и ИИ · **S3** подключение новых бизнесов · **S4** безопасность и регуляторы · **S5** надёжность.

## 1. Логика последовательности

1. **Сначала договориться и защитить данные.** Без согласованных границ доменов, списка допустимых данных и модели ролей открывать витрину нельзя.
2. **Затем фундамент** (облако, интеграция, безопасность): на нём стоит всё остальное.
3. **Потом платформа данных и первые отчёты**: быстрый видимый результат для бизнеса уже в середине года.
4. **Затем развязка доменов:** финтех и ИИ уходят от DWH. Шина (ESB) не «заменяется одной Kafka», а разбирается по функциям: доставка, проверки формата и смысла, преобразования, надёжность, бизнес-логика. Потоки переводятся по одному.
5. **В конце масштабирование и закрепление:** партнёры, портал для всех, аварийное восстановление, перевод аналитической части DWH в архив.

Подход к миграции постепенный: старое DWH работает параллельно, пока цифры новых отчётов не совпадут со старыми.

**Важное правило про клиники.** Старое DWH делится на две части. Аналитическая часть переводится в «только чтение» и затем в архив. Клинический контур легаси (PowerBuilder и данные, в которые клиники пишут приёмы и медкарты) продолжает работать с записью. Запись в него закрывается для клиники не по дате, а когда выполнены условия проверенного переноса клинических операций (см. [clinical_contour.md](../Task1/clinical_contour.md)). Совпадение аналитических отчётов этого не заменяет.

## 2. Этапы

### Этап 1. Согласовать и подготовить (месяцы 0–2)

**Цель бизнеса:** согласованная архитектура, границы доменов и план (цель «через пару месяцев»).

| Что делаем | Результаты |
|------------|------------|
| Утверждаем домены, контракты и правила обмена (Задание 2) | Документ границ доменов и реестр контрактов |
| Классифицируем данные, фиксируем список допустимых полей для платформы (медданные исключены), модель ролей | Политика допуска данных и матрица ролей |
| Выбираем облако по требованиям регулятора, стоимости, компетенциям; строим базовую среду | Выбранный провайдер, ландинг-зона, IaC и CI/CD в работе |
| Инвентаризируем потоки, отчёты и логику в DWH; составляем план миграции | Реестр отчётов и потоков, план миграции по доменам |
| Инвентаризируем маршруты ESB (Camel): что делает каждый — доставка, проверки, преобразования, бизнес-логика, повторы; делим на классы | Реестр маршрутов с владельцами и очередью миграции по риску ([esb_migration.md](../Task1/esb_migration.md)) |
| Инвентаризируем клинические операции, которые **пишут** данные (запись на приём, приём, назначения, правки медкарты, результаты) | Перечень операций с частотой и владельцами: основа списка для новой клинической системы |
| Выбираем 10–15 приоритетных отчётов для первого запуска портала | Утверждённый список вместе с владельцами |
| Определяем владельцев данных (Data Stewards) по доменам | Назначенные ответственные |

**Ответственные:** архитектурная группа (лидер), ИБ и комплаенс, платформенная инженерия, представители доменов, владельцы данных, PMO.
**Ресурсы:** около 18 человек (часть из них не на полную ставку); облачная среда на уровне разработки и тестирования; рабочие встречи с руководителями направлений и регулятором.
**Решение в конце этапа:** руководство утверждает архитектуру, домены и бюджет следующего этапа.

### Этап 2. Платформа и первые отчёты (месяцы 2–6)

**Цель бизнеса:** первые отчёты за минуты и безопасный доступ в рамках ролей (S1, S4).

| Что делаем | Результаты |
|------------|------------|
| Облако: Kubernetes, Kafka, реестр схем, очередь ошибок, API Gateway, единый вход, шифрование, ключи | Работающая среда с SSO и шифрованием данных |
| Camel начинает дублировать данные в Kafka (мост); поднимаем потоковую обработку (Kafka Streams) для проверок и преобразований | Новая платформа читает данные из Kafka, старые потребители работают как раньше |
| Клинические данные выносятся в **отдельную БД** (с записью), PowerBuilder переключается на неё; разработка клинической информационной системы по списку операций | Аналитическую часть DWH можно переводить в чтение, не останавливая клиник |
| Ядро платформы: озеро (Iceberg), загрузка (Debezium, Kafka Connect), dbt, ClickHouse, оркестрация | Первые домены (финтех — обезличенные показатели, головной офис) публикуют данные в платформу |
| Каталог данных, проверки качества, семантический слой | Единые определения метрик, каталог и проверки качества включены |
| MVP портала самообслуживания и BI на семантическом слое | Приоритетные отчёты доступны пилотной группе, строятся за минуты |
| Начало миграции истории DWH в озеро; параллельная работа с DWH и сверка | Результаты новых отчётов совпадают со старыми |
| Резервное копирование и базовый план аварийного восстановления для критичных систем | Резервные копии включены, план утверждён |

**Ответственные:** команда платформы данных (лидер), платформенная инженерия, ИБ, доменные команды финтеха и головного офиса, QA и сверка данных, Data Stewards.
**Ресурсы:** около 30–35 человек; облако: озеро данных (хранение сотен ТБ нарастает постепенно), вычисления под трансформации и витрины, среды разработки, тестирования и промышленная; в основном открытое ПО, коммерческая поддержка по необходимости.
**Решение в конце этапа:** пилотная группа бизнеса принимает MVP портала; расхождения со старыми отчётами устранены или объяснены.

### Этап 3. Развязать домены (месяцы 6–9)

**Цель бизнеса:** финтех и ИИ развиваются независимо от DWH и друг от друга (S2, S3, S5).

| Что делаем | Результаты |
|------------|------------|
| Финтех: логика из DWH переезжает в сервисы, собственная БД, события по контрактам | Релизы финтеха выходят без правок в DWH |
| ИИ: развязка от DWH, MLflow, обмен с клиниками через API Gateway | Релизы моделей независимы от остальных систем |
| Головной офис: сервисы персонала, инвентаризации, закупок, события | Показатели головного офиса поступают в платформу событиями |
| Потоки Camel переводятся на Kafka и шлюз **по одному** (сначала аналитика, затем ИИ, финтех последним): параллельный запуск не менее 2 недель, сверка, переключение, откат. Бизнес-логика из маршрутов уходит в сервисы доменов, многошаговые процессы становятся сагами | Основные потоки не зависят от старой шины; у каждого потока контракт, владелец и очередь ошибок |
| Аналитическая часть DWH переходит в режим «только чтение» (клинический контур работает с записью) | Аналитика не зависит от старой базы, клиники не затронуты |
| Мониторинг, журнал доступа к данным, отчёты для аудита | Видно, кто и когда работал с данными |
| Расширение портала на новые направления, конструктор отчётов, обучение пользователей | Большая часть направлений работает с порталом |

**Ответственные:** доменные команды финтеха, ИИ и головного офиса (лидеры работ в своих доменах), платформенная инженерия, команда платформы данных, ИБ.
**Ресурсы:** около 40–46 человек (пик нагрузки); дополнительная инфраструктура для доменных баз и ИИ; обучение сотрудников работе с порталом и новыми инструментами.
**Решение в конце этапа:** демонстрация независимого релиза финтеха и ИИ без правок в DWH.

### Этап 4. Масштабировать и закрепить (месяцы 9–12)

**Цель бизнеса:** подключение новых бизнесов без правок в DWH, работающий портал, подтверждённая надёжность (S1, S3, S4, S5).

| Что делаем | Результаты |
|------------|------------|
| Шаблон домена партнёра и пилот первого партнёра (фарма или электроника) | Партнёр подключён по шаблону; аналитика по нему появилась без отдельной разработки |
| Портал v1 для всех направлений | Бизнес-пользователи доменов работают с данными самостоятельно |
| Аварийное восстановление: учения и проверка целевых сроков восстановления | Критичные системы клиник и банка проходят проверку |
| Аудит безопасности и соответствия требованиям (включая проверку allow-list и доступа) | Отчёт аудита, устранённые замечания |
| Аналитическая часть DWH: архив после сверки | Решение принято на основании сверки отчётов |
| Пилот новой клинической системы в одной клинике: параллельная работа не менее 4 недель, сверка данных, откат | Подтверждено покрытие клинических операций и перенос данных без потерь |
| Camel отключается, когда нет активных маршрутов и клинических потоков на нём | Старая шина выключена |

**Ответственные:** домен партнёров и головной офис, команда платформы данных, ИБ и комплаенс, платформенная инженерия, команда клиник.
**Ресурсы:** около 40–44 человек; площадка аварийного восстановления в другой зоне; внешний аудит или пентест.
**Решение в конце этапа:** архив аналитической части DWH и график переноса клиник по одной. Запись в клинический контур **не отключается**, пока для клиники не выполнены условия проверенного переноса (покрытие операций, сверка данных, пилот, права и защита, обучение, отказоустойчивость, готовый откат).

| Мера | Этап | Зачем |
|------|------|-------|
| Исключение медицинских данных из платформы (allow-list), классификация данных | 1 | Соблюдение решения бизнеса и требований регуляторов |
| Единый вход, роли, ограничение строк | 2 | Сотрудники видят только своё |
| Шифрование данных, управление ключами | 2 | Защита медицинской и банковской тайны |
| Резервное копирование критичных БД | 2 | Защита от потерь |
| Журнал доступа и отчёты аудита | 3 | Прозрачность для регулятора |
| Параллельная работа DWH и платформы, сверка отчётов | 2–4 | Миграция без потери качества и данных |
| Условия отключения записи в клинический контур (покрытие операций, сверка данных, пилот, откат) | 4 и далее | Клиники не теряют возможность сохранять приёмы и медкарты |
| Параллельный запуск и сверка каждого потока ESB, откат до выключения старого пути | 3–4 | Нет потерь и двойных списаний при переключении |
| Аварийное восстановление: учения | 4 | Клиники и банк остаются доступны при сбоях |
| Внешний аудит безопасности | 4 | Независимое подтверждение |

| Платформа данных | 2 | 6–8 | 6–8 | 5–6 |
| Платформенная инженерия | 3 | 5–6 | 5 | 4 |
| ИБ и комплаенс | 2 | 3 | 3 | 3–4 |

| Головной офис | 1 | 1 | 2–3 | 2 |
| Клиники | 1 | 2–3 | 4–5 | 5–7 |
| Партнёры | 0 | 0 | 1 | 3 |
| Data Stewards | 2 | 4 | 5 | 6 |
| QA и сверка данных | 0 | 2 | 3 | 3 |
| PMO и владелец портала | 2 | 2 | 2 | 2 |
| **Итого** | **18** | **30–35** | **40–46** | **40–44** |

Прочие ресурсы:

- **Инфраструктура:** облачные среды (разработка, тестирование, промышленная), озеро данных, вычисления, площадка аварийного восстановления; расходы нарастают по мере переноса данных и частично компенсируются отключением старого оборудования и лицензий.
- **ПО:** преимущественно открытые продукты; коммерческая поддержка по необходимости. Решение о Power BI Service или Superset принимается на этапе 1.
- **Обучение:** команды (новый стек, доменный подход) и бизнес-пользователи (портал).
- **Внешние услуги:** аудит безопасности и пентест на этапе 4, возможно консультанты по облаку.
- **Денежная оценка** составляется на этапе 1 после выбора облака и уточнения объёмов данных.

## 6. Зависимости и риски плана

| Риск или зависимость | Как снижаем |
|----------------------|-------------|
| Решения этапа 1 затягиваются, сдвигается всё | Жёсткий срок утверждения, решение руководства по спорным вопросам |
| Выбор облака и требования регулятора | Анализ требований до выбора; рассмотреть гибридный вариант |
| Расхождение цифр новых и старых отчётов | Параллельная работа и сверка; решение об отключении только после совпадения |
| Закрытие записи в DWH остановит клиники: совпадение отчётов этого не показывает | Клинический контур отделён и работает с записью; отключение для каждой клиники только по условиям проверенного переноса |
| В маршрутах Camel скрыта бизнес-логика, проверки или повторы | Инвентаризация маршрутов, перевод по одному, параллельный запуск со сверкой |
| Пилот клиники затягивается | Клинический контур не мешает аналитике (отдельная БД); срок года не требует полной замены PowerBuilder |
| Нехватка людей с новыми компетенциями | Обучение, шаблоны, привлечение внешних специалистов |
| Пик нагрузки на этапе 3 | Планировать отпуска и релизы заранее, ограничить параллельные проекты |
| Сопротивление пользователей смене привычного BI | Обучение, пилотная группа, быстрые победы |
| Утечка через самообслуживание | Роли, allow-list, журнал доступа, аудит на этапе 4 |
