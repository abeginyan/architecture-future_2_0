# Задание 2. Разделение системы на домены

Сценарии (те же метки, что в Задании 1): **S1** быстрая отчётность · **S2** независимое развитие финтеха и ИИ · **S3** подключение новых бизнесов · **S4** безопасность и регуляторы · **S5** надёжность.

## 1. По каким правилам проводились границы

Домен — это часть бизнеса, у которой есть свои данные, своя логика, своя команда и свои правила изменений. Границы проведены по пяти признакам:

1. **Бизнес-возможность.** Что именно делает эта часть компании (лечит, диагностирует, проводит платежи, управляет сетью, торгует с партнёрами).
2. **Владелец данных.** У каждого набора данных ровно один домен-хозяин. Остальные получают его только через API или события.
3. **Требования к безопасности.** Медицинские и банковские данные имеют разные режимы защиты и разных регуляторов, поэтому лежат в разных доменах.
4. **Скорость изменений.** Часто меняющиеся направления (финтех-продукты, ИИ-модели) не должны зависеть от редко меняющихся (учёт персонала).
5. **Команда.** Один домен — одна команда, которая может выпускать релизы без согласования с остальными.

## 2. Домены

| № | Домен | Что делает | Чем владеет (данные) | Основные потребители | Какие сценарии поддерживает |
|---|-------|-----------|----------------------|----------------------|------------------------------|
| 1 | **Клиники** | Приём пациентов, медкарты, назначения, снимки; заменяет интерфейс PowerBuilder | Медицинская БД, хранилище снимков | ИИ-домен (через API), домен финтеха (только счёт без медданных) | S2, S4 |
| 2 | **ИИ-сервисы** | Анализ медицинских данных и снимков, рекомендации врачу, управление моделями | Реестр моделей, метрики качества моделей | Клиники | S2, S4 |
| 3 | **Финтех / Банк** | Счета, платежи, кредиты; новые финансовые продукты | Банковская БД (финансовая история, счета, кредиты) | Клиники (оплата лечения), платформа данных (обезличенные показатели) | S2, S3 |
| 4 | **Головной офис** | Персонал, инвентаризация, закупки, управление клиниками, финансовая отчётность | БД головного офиса | Партнёры (заявки на закупку), платформа данных | S1, S3 |
| 5 | **Партнёры (шаблон)** | Обмен с фармацевтикой и производителем электроники: поставки, заказы, цены. Для каждого партнёра создаётся свой экземпляр по шаблону | БД партнёрского домена | Головной офис, платформа данных | S3 |
| 6 | **Интеграция и безопасность** | API Gateway, шина событий, реестр схем, единый вход и роли, мастер-данные клиентов и согласия, журнал доступа | Мастер-данные клиентов (единый ID), согласия, реестр контрактов | Все домены | S2, S3, S4, S5 |
| 7 | **Платформа данных (витрина)** | Загрузка данных из доменов, трансформации, каталог, самообслуживание, отчёты | Озеро данных, витрины, каталог (копии разрешённых наборов, не оригиналы) | Бизнес-пользователи | S1, S3, S4 |

**Старое DWH** отдельным доменом не является. Оно переходный объект: историю переносим в озеро данных (домен 7), операционные данные возвращаются в домены-владельцы, затем DWH отключается.

## 3. Как домены связаны

| Откуда | Куда | Что передаётся | Как | Чего не передаётся |
|--------|------|----------------|-----|--------------------|
| Клиники | ИИ | Запрос анализа: псевдоним пациента, данные исследования, временная ссылка на снимок | API через шлюз | Лишние персональные данные |
| ИИ | Клиники | Заключение и рекомендации | API через шлюз | — |
| Клиники | Финтех | Счёт за лечение: сумма, идентификатор клиента | Событие или API | Диагнозы и любые медицинские детали |
| Домены 1, 3, 4, 5 | Платформа данных | Разрешённые показатели (загрузка, выручка, остатки, платежи) | События Kafka, загрузка по allow-list | Медкарты, истории болезней, результаты исследований |
| Головной офис | Партнёры | Заявки на закупку, остатки | События | Персональные данные сотрудников |
| Партнёры | Головной офис, платформа данных | Поставки, цены, статусы заказов | События по шаблону | Внутренние данные партнёра сверх договора |
| Все домены | Интеграция и безопасность | Запросы на вход, проверка прав, согласия | OIDC / API | — |

## 4. Правила взаимодействия доменов

1. **Данные принадлежат домену.** Чужую базу напрямую никто не читает. Только API или события.
2. **Контракты зафиксированы.** Формат событий и API хранится в реестре схем и версионируется. Менять контракт можно только совместимо или с переходным периодом.
3. **В платформу данных идёт только то, что разрешено.** Каждый домен публикует свои data products по списку допустимых полей. Медицинские данные в список не включаются.
4. **Единый идентификатор клиента.** Пациент и клиент банка связываются через мастер-данные с учётом согласий. Прямого обмена персональными данными между клиникой и банком нет.
5. **Бизнес-логика остаётся в своём домене.** В платформу данных попадает только аналитическая логика (расчёт метрик). Ничего операционного туда не добавляется. То же верно и для остатков DWH.
6. **Новый бизнес подключается по шаблону**, не требуя изменений в других доменах (кроме регистрации контракта в домене 6).

## 5. Проверка границ: что меняется при типовых изменениях

| Изменение | Затрагиваемые домены | Нужно ли менять DWH или платформу |
|-----------|----------------------|------------------------------------|
| Новый финтех-продукт (рассрочка на лечение) | Только 3; в 6 регистрируется контракт | Нет. Показатели автоматически попадают в платформу после включения в allow-list |
| Новая версия ИИ-модели | Только 2 | Нет |
| Подключение фармацевтической компании | Новый экземпляр домена 5; в 6 регистрируются контракты | Нет. Витрина добавляется в платформе как новый data product |
| Новый показатель в отчёте | Только 7 (метрика в семантическом слое) | Нет |
| Новый отчёт для руководителя клиники | Только 7 (самообслуживание) | Нет |
| Смена интерфейса оператора | Только 1 | Нет |
