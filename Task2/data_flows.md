# Задание 2. Потоки данных (пояснение к DFD)

Диаграмма: [DFD.png](DFD.png), исходник [DFD.puml](DFD.puml). Цвет стрелки соответствует сценарию. Номера потоков (A1, B3 и т. д.) совпадают с подписями на диаграмме.

Обозначения: прямоугольник — внешний участник; овал — процесс (номер соответствует домену); цилиндр — хранилище; пунктирная рамка — домен.

## Сценарий A (красный). ИИ анализирует медицинские данные

Цель: врач получает заключение ИИ, а медицинские данные не покидают контур клиники и ИИ-сервиса и не попадают в платформу данных.

| Поток | Откуда → куда | Что передаётся | Комментарий |
|-------|---------------|----------------|-------------|
| A1 | Врач → 1.0 | Данные осмотра, запрос на ИИ-анализ | Через интерфейс клиники |
| A2 | 1.0 → D2 | Снимки | Хранятся в домене клиник |
| A3 | 1.0 → 6.0 | Запрос анализа: псевдоним пациента, данные исследования, ссылка на снимок | Только через шлюз, с проверкой прав |
| A4 | 6.0 → 2.0 | Запрос | Шлюз передаёт ИИ-сервису |
| A5 | D3 → 2.0 | Актуальная версия модели | Реестр моделей |
| A6 | D2 → 2.0 | Снимок по временной ссылке | Ссылка живёт ограниченное время |
| A8 | 2.0 → 6.0 | Заключение ИИ (вероятные диагнозы, рекомендации) | |
| A9 | 6.0 → 1.0 | Заключение | |
| A7 | 1.0 → D1 | Карта пациента и заключение | Сохраняется после подтверждения врачом |

Нумерация A7–A9 условная; по времени A7 выполняется последним.

**Принятое допущение:** ИИ-домен не хранит медицинские данные дольше обработки запроса; в собственных журналах остаются только обезличенные метрики. Конкретные сроки уточняются требованиями регулятора.

## Сценарий B (синий). Подключение нового финтех-сервиса (пример: рассрочка на лечение) и оплата лечения

Цель: запустить новый финансовый продукт, не меняя ни DWH, ни другие домены.

| Поток | Откуда → куда | Что передаётся | Комментарий |
|-------|---------------|----------------|-------------|
| B1 | Клиент банка ↔ 3.1 | Заявка, условия, решение | Новый сервис работает с клиентом напрямую |
| B2 | 3.1 → 9.0 | Проверка клиента и его согласия | Единый идентификатор клиента |
| B3 | 3.1 ↔ D4 | Договоры, платежи | Собственная схема в банковской БД |
| B4 | 1.0 → 6.0 | Счёт за лечение (сумма, идентификатор клиента) | Без медицинских данных |
| B5 | 6.0 → 3.0 | Запрос оплаты | |
| B6 | 3.0 ↔ D4 | Счета, кредиты | |
| B7 | 3.1 → 6.0 | События по зарегистрированному контракту | Контракт в реестре схем |
| B8 | 3.0 → 6.0 | События платежей | |

**Шаги подключения нового сервиса:** (1) зарегистрировать контракт событий и API в домене 6; (2) подключить сервис к единому входу и мастер-данным клиентов; (3) опубликовать показатели в Kafka; (4) домен 7 включает показатели в свои витрины. Правок в DWH и в других доменах не требуется.

## Сценарий D (оранжевый). Подключение партнёров (фарма, электроника)

Цель: добавить партнёра как новый экземпляр шаблона домена.

| Поток | Откуда → куда | Что передаётся | Комментарий |
|-------|---------------|----------------|-------------|
| D1 | Партнёр ↔ 5.0 | Поставки, заказы, цены | |
| D2 | 5.0 ↔ D8 | Данные партнёра | Собственное хранилище |
| D3 | 5.0 → 6.0 | События по шаблону | Формат по контракту |
| D4 | 4.0 → 6.0 | Заявки на закупку, остатки | Головной офис заказывает |

Аналитика по партнёру появляется в платформе данных тем же путём, что и в сценарии C (потоки C1–C3), без отдельной разработки.

## Прочие потоки (серый)

| Поток | Откуда → куда | Что передаётся |
|-------|---------------|----------------|
| E1 | 4.0 ↔ D5 | Персонал, инвентарь |
| E2 | 4.0 → 6.0 | События и показатели головного офиса |
| E3 | 9.0 ↔ D9 | Единый идентификатор, согласия |
| E4 | 1.0 → 9.0 | Вход пользователей, роли |
| E5 | 1.0 → 6.0 | Операционные показатели клиники (загрузка, выручка) без медданных |

## Что принципиально не передаётся

- Медкарты, истории болезней и результаты исследований в домен 7 (платформа данных) не попадают ни одним потоком.
- Прямых потоков между клиникой и банком с персональными данными нет: только счёт через шлюз.
- Прямого чтения чужих баз данных нет: все потоки идут через шлюз или шину.
