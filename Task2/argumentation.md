# Задание 2. Аргументация разделения на домены

## 1. Почему именно такое разделение

Сегодня всё держится на одном DWH: там данные всех направлений и значительная часть бизнес-логики, а все системы связаны через одну шину. Поэтому любое новое направление или продукт означает доработку DWH, а отчёты строятся часами. Разделение по доменам убирает эту зависимость.

| Домен | Почему выделен отдельно | Бизнес-сценарий, который он поддерживает |
|-------|-------------------------|-------------------------------------------|
| Клиники | Свои данные (медицинские, самые чувствительные), свои пользователи, свои правила хранения | Лечение, качество медицинских услуг, S4 |
| ИИ-сервисы | Часто обновляются модели, другой стек (Python), другой цикл релизов | Независимое развитие ИИ, S2 |
| Финтех / Банк | Своя лицензия и регулятор, стек Go и Java, быстро меняющиеся продукты | Независимое развитие финтеха, S2, S3 |
| Головной офис | Редко меняющиеся общие функции (персонал, инвентарь, закупки) | Управление сетью, S1 |
| Партнёры (шаблон) | Партнёры приходят один за другим, каждому нужен одинаковый способ подключения | Новые бизнесы, S3 |
| Интеграция и безопасность | Общие правила для всех: вход, роли, контракты, аудит. Если их размазать по доменам, получится хаос | Безопасность и надёжность, S4, S5 |
| Платформа данных | Аналитика по всем доменам; не должна менять операционные системы и не должна видеть медицинские данные | Быстрая отчётность, S1 |

## 2. Преимущества для бизнеса

### 2.1. Ускорение вывода продуктов

- Новый финтех-продукт делается внутри домена 3 и регистрирует контракт в домене 6. Не нужно согласовывать изменения со всеми остальными и дорабатывать DWH.
- Новая версия ИИ-модели выпускается внутри домена 2 без остановки клиник, пока контракт API сохраняется.
- Новые отчёты и метрики создаются в домене 7 самими аналитиками через самообслуживание, без очереди в IT.
- Партнёр подключается по готовому шаблону, а не отдельным интеграционным проектом.

### 2.2. Снижение зависимости от DWH

- Операционная логика возвращается в доменные сервисы; в аналитической части остаются только расчёты метрик.
- DWH перестаёт быть единственным местом, где можно «посмотреть данные»: у каждого домена есть собственный источник истины, а общая картина собирается в платформе данных.
- DWH можно отключать поэтапно: сначала только чтение, потом перенос истории, потом архив. Остановка DWH перестаёт быть остановкой всей компании.

### 2.3. Независимое развитие направлений

- У каждого домена своя команда, стек, расписание релизов и собственная база.
- Сбой в одном домене не должен останавливать другие: общение асинхронное (события), а шлюз и шина отказоустойчивы и развёрнуты в нескольких зонах.
- Каждое направление может расти и масштабироваться в своём темпе: нагрузка ИИ-анализа не влияет на работу банка.

### 2.4. Целостная картина показателей сохраняется

Разделение не ломает общую отчётность. Платформа данных собирает разрешённые показатели из всех доменов, а единый семантический слой и каталог гарантируют одинаковые определения метрик. Руководство по-прежнему видит ключевые бизнес-показатели целиком.

### 2.5. Безопасность и соблюдение требований

- Медицинские и банковские данные физически разделены и защищаются по своим правилам.
- В платформу данных попадает только список разрешённых полей. Медицинские данные не включаются по решению бизнеса.
- Единый вход, роли и журнал доступа дают регулятору прозрачную картину: кто, когда и какие данные использовал.

## 3. Было и стало

| Вопрос | Сейчас | После разделения |
|--------|--------|------------------|
| Новый финтех-продукт | Правки в DWH и шине, согласование с несколькими командами | Работа внутри домена финтеха, регистрация контракта |
| Новое направление (фарма) | Отдельный проект по доработке DWH | Копия шаблона домена, события по стандарту |
| Новый отчёт | Заявка в IT, доработка схемы DWH, отчёт строится часами | Самообслуживание в платформе данных, быстрые витрины |
| Сбой шины | Останавливаются все связи | Влияние ограничено: события буферизуются, домены продолжают локальную работу |
| Доступ к медицинским данным | Все данные в одной БД | Только домен клиник и ИИ-сервис по запросу врача |
| Выход из строя DWH | Критичный риск для всего бизнеса | Влияет только на историческую аналитику, пока не отключено окончательно |

## 4. Рассмотренные альтернативы

| Вариант | Почему не выбран |
|---------|------------------|
| Оставить единое DWH и разделить его на схемы или БД по направлениям | Остаются общая технология SQL Server 2008, общая логика в базе и общий релиз. Проблемы отчётности и независимости развития не решаются |
| Разделить по технологиям (отдельно Go, Java, Python) | Границы не совпадают с бизнес-возможностями, команды всё равно зависят друг от друга |
| Разделить только по юридическим лицам (четыре подразделения) | Слишком грубо: интеграция, безопасность и аналитика остаются «ничьими», а подключение новых бизнесов не решается |
| Один домен под все данные для аналитики (Data Lake без доменов) | Тот же центральный монолит, только в облаке; нет владельцев данных |

## 5. Риски и как их снизить

| Риск | Как снижаем |
|------|-------------|
| Сложность распределённой системы (много сервисов, события) | Единые стандарты, шаблоны, мониторинг и трассировка в домене 6 |
| Расхождение данных между доменами | Единый идентификатор клиента, реестр схем, проверки качества в платформе данных |
| Разные определения метрик | Единый семантический слой и каталог данных; владельцы данных назначаются по доменам |
| Нужны новые компетенции у команд | Обучение, шаблоны доменов, платформенная команда |
| Миграция истории (сотни ТБ) | Поэтапная миграция по доменам, параллельная работа и сверка результатов |
| Утечки через самообслуживание | Роли и ограничение строк, allow-list полей, журнал доступа |

## 6. Как проверять, что разделение работает

Ориентировочные показатели для оценки (конкретные значения уточняются после пилота):

- время подготовки типового сложного отчёта (цель: минуты вместо часов);
- срок выхода нового финтех-продукта и срок подключения нового партнёра;
- число изменений в DWH или платформе, нужных для запуска нового продукта (цель: ноль);
- доля отчётов, которые бизнес собирает сам без IT;
- число инцидентов доступа к данным вне прав пользователя (цель: ноль).
